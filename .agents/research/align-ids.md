## Answer

Under rule B, **32 v2 rows clearly state the same rule as a v1 row** and should take the v1 id. Most are plain one-to-one renames. Only `ACP-ERROR-201`/`ACP-RESUME-211` need re-splitting to match v1's ERROR-003/004 split. **8 rows are borderline.** In each one, the v2 row folds two v1 rows together, splits one v1 row in two, or moves the turn-end carrier from the prompt response to an idle `state_update`. The user should decide each of those. All other 2xx rows were checked and have no v1 row stating the same rule. The 30 ids already shared are all the same rule in both versions: no conflicts. No proposed target collides with a live v2 id, an id removed in this change, or any id v2 has ever defined, with one exception. `ACP-PROMPT-003` was v2's own id for this exact rule until `b8c2e49`, which predates this update, so renaming `PROMPT-206` back to it reuses no freed number. One stale text needs fixing whatever is decided: `ACP-PROMPT-205` states the rejected "changed tier needs a fresh id" convention.

## Details: clear renames (rows 1-32)

The v1 and v2 spec sentences are the same, or differ only in a method/field rename or the RFC keyword. Under rule B, tier and gate are per version, so a SHOULD -> MUST change does not block a rename. For each row: the v1 row text, the v2 row text, the spec evidence, and any text edits the rename forces.

1. **TRANSPORT-201 -> TRANSPORT-001.** v1: "Every line … is a single valid JSON-RPC 2.0 message." v2: "… a single JSON-RPC 2.0 message object; a JSON array … is non-conformant". Spec: v1 `transports.mdx:20` "Messages are individual JSON-RPC requests…" and v2 `:20` "Each message is a single … object" are the same rule. v2 adds the explicit no-batch rule at `:67`, which v1 `transports.mdx` does not mention (`grep -i batch` finds nothing). ## Details: borderline rows (33-40), with trade-offs

**33. AUTH-204 -> AUTH-003 (lean rename).**
- v1 AUTH-003: after a successful `authenticate`, `session/new` does not fail `-32000`.
- v2 AUTH-204: given `--auth-method`, `auth/login` is not `-32601` (v2 `authentication.mdx:51` "MUST implement both") and not `-32602` for an `agent` method (`:191`). Then `session/new` is not `-32000` (`:193-195`).
- *For rename:* the row says "Mirrors v1's `ACP-AUTH-003`, method renamed". Both are "the drive-a-real-login" row, and the extra checks are preconditions of "a successful login".
- *Against:* the shared id then also carries v2's "MUST implement `auth/login`", which v1 has no counterpart for.
- *Strict alternative:* split the method-existence checks into a new 2xx row. That is a test change, beyond a rename.

**34. AUTH-207 -> AUTH-006 (lean rename).**
- v1 AUTH-006: with `clientCapabilities.auth.terminal: true`, the `initialize` result validates, including `terminal` entries' `args` (string array) and `env` (string map).
- v2 AUTH-207: with `capabilities.auth.terminal: {}`, `terminal` entries' `args` is a string array, `env` is an array of `EnvVariable`, and env names are unique.
- *For:* same rule, "terminal descriptors are well-formed". Uniqueness only became a separate check because v2 turned `env` from a map into an array; in v1, the map's keys already make names unique in practice.
- *Against:* the v1 row is broader (the whole `initialize` result, plus the `type`-discriminator check).
- **Independent fix:** AUTH-207's text says "New in v2 -- v1's terminal auth descriptor had no `args`/`env` fields". That is false at 3961af94: v1 `$defs/AuthMethodTerminal` has `args` (array of string) and `env` (object, string values).

**35. AUTH-209 -> AUTH-007 (+ AUTH-008).**
- v1 has two rows and two tests (`v1 test_authentication.py:215`, `:235`):
  - AUTH-007 (CAPABILITY): the result validates and is never an error or `-32000`.
  - AUTH-008 (ADVISORY): `state` is a known value or `_`-prefixed.
- v2 folds both into one test (`v2 test_authentication.py:290`, three assertions in sequence). The `AuthState` schema is identical in both versions.
- Option (a), rename AUTH-209 -> AUTH-007: the cheapest. But v2's AUTH-007 would then also fail on the `state` rule, which v1 keeps under AUTH-008. That is not strictly "the same rule".
- Option (b), the strict version: split the v2 test into AUTH-007 (validity, not `-32000`/`-32601`) and AUTH-008 (state closure, tier per v2's own judgment). AUTH-209 is freed.
- Option (c): leave it as a v2-only fold.
- I recommend (b) if the user wants strict alignment, and (a) otherwise.

**36. CONFIG-204 -> CONFIG-001 (lean rename).**
- v1 CONFIG-001: every `configOptions` entry's `currentValue` is legal for its type (bool for `boolean`, one of `options` for `select`), "derived from the field descriptions". v1 `:118-130` has no RFC keyword on membership.
- v2 CONFIG-204: a `select` option's `currentValue` is one of its options. v2 `:130` adds an explicit MUST.
- In v2, the boolean-type half falls to CONFIG-201's shape check.
- *For:* the core rule, "`currentValue` is a legal value of its option", is the same, and the select half is the substantive part.
- *Against:* v2 CONFIG-204 is narrower than v1 CONFIG-001.

**37. CONFIG-207 + CONFIG-208 vs ERROR-007 (merge, or leave).**
- v1 ERROR-007 (ADVISORY, three tests: `v1 test_errors.py:351,375,401`): unknown `modeId`, unknown `configId`, and unsupported select value all get `-32602`.
- v2 has no modes. CONFIG-207 (unknown `configId`) and CONFIG-208 (undeclared value, type mismatch, unsupported type) both come from one sentence, v2 `session-config-options.mdx:234`. The `error.mdx` invalid-params sentence also appears in both versions (v1 `:47`, v2 `:48`).
- Neither v2 row alone states v1's rule, so a one-to-one rename is wrong.
- Option (a), merge both into ERROR-007: strict alignment. Two v2 test functions get the marker, CONFIG-207/208 are freed, and CONFIG-209's text ("probes of `ACP-CONFIG-207`/`208`", `requirements.py:2275,2278`) must be reworded. The cost: you lose per-probe report granularity, and fixtures `config_set_unknown_id_accepted.py` / `config_set_invalid_value_wrong_code.py` would no longer FAIL distinct ids in `test_cli.py`.
- Option (b), leave: each v2 row is a strict subset of v1 ERROR-007, and the 2xx ids then mean "narrower v2 rows".
- I recommend (a) only if the user wants every v1-traceable rule under its v1 id. Otherwise (b).

**38-39. CANCEL-201 -> CANCEL-001, CANCEL-202 -> CANCEL-002 (decide together).**
- The spec paragraphs are sentence-for-sentence parallel:
  - v1 `prompt-turn.mdx:645` "MUST respond to the original `session/prompt` request with the `cancelled` stop reason" ↔ v2 `prompt-lifecycle.mdx:1185-1187` "MUST send an idle `state_update` … with the `cancelled` stop reason".
  - v1 `:652` "MUST catch these errors and return … `cancelled`" ↔ v2 `:1199`.
  - v1 `:656` "updates … before responding to the `session/prompt` request" ↔ v2 `:1203` "… before sending the idle `state_update` that reports cancellation".
- *For:* the same rules with the carrier swapped. That is the same kind of change as `authenticate` -> `auth/login`, which we treat as the same rule.
- *Against:* v1 and v2 have different turn-end contracts (CLAUDE.md: "genuinely different turn-end contracts"), and a reader may expect a shared id to be checked the same way.
- Mapping wrinkle: v1 CANCEL-001 cites both `:645` and `:652`. In v2, `:1199` ("not `error`") belongs to CANCEL-203, which also carries v2-only `-32800`-before-insertion logic. So CANCEL-201 -> CANCEL-001 maps the main half and CANCEL-203 stays 2xx.
- I lean rename for both. If the user rejects 38, reject 39 too for consistency.

**40. INIT-201 vs INIT-002 (lean leave).**
- v1 INIT-002: a request of 1 returns 1. v1 `initialization.mdx:99`: "If the Agent supports the requested version, it MUST respond with the same version."
- v2 INIT-201 checks v2 `:110`: "MUST select the highest … ≤ the requested version". Its assertions are "≤ 2" and "equals the 65535 selection when ≤ 2". v2 `:110` repeats v1's echo as a corollary ("If it supports the requested version, this selects that version").
- *For rename:* the corollary is v1's rule.
- *Against:* v2 replaced the negotiation algorithm. v1's "otherwise latest" becomes v2's "≤ requested, else `-32022`". INIT-201 also judges the non-supported case.
- The already-shared `ACP-INIT-003` is fine either way: both rows probe "above every supported version", where the two algorithms agree.
